## Context

仓库当前使用 Next.js 16.2.9、React 19.2.4、TypeScript 5、ESLint 9 和 Node 原生测试运行器。基线盘点显示 `npm test` 的 79 个测试全部通过，`npx tsc --noEmit` 通过，但 `npm run lint` 报告 15 个错误和 10 个警告，问题横跨组件、服务与 API 路由。当前 `package.json` 没有独立的 `typecheck` 或聚合质量命令，也没有一条能代表完整交付健康度的单一入口。

本变更由实现代理接手时，凡涉及 Next.js 或 React 代码，必须先阅读 `node_modules/next/dist/docs/` 中与 App Router、客户端组件、数据获取和错误处理相关的当前版本指南，不能依赖旧版 Next.js 经验。

## Goals / Non-Goals

**Goals:**

- 在不改变既有产品行为的前提下，将 ESLint 基线清理到零错误、零警告。
- 用根因修复替代全局关规则、批量忽略或扩大 `any` 的做法。
- 建立可由开发者和自动化环境共同调用的统一质量入口。
- 保持类型检查、79 个现有测试及生产构建通过，并为高风险重构补充回归测试。
- 将执行顺序和验收证据拆成适合 Reasonix 接手的实现步骤。

**Non-Goals:**

- 不新增产品功能，不重做家谱画布、搜索或设置页视觉设计。
- 不修改 Prisma schema、迁移历史或公开 API 契约。
- 不以追求任意覆盖率数字为目标，也不在本次变更中更换测试框架。
- 不顺带重构与 lint 债务无关的模块。

## Decisions

### 1. 以零告警作为 lint 基线

统一 lint 命令应显式拒绝 warning，确保现有 10 个警告也被真正清理，而不是在 CI 中悄悄积累。优先删除未使用代码、收窄类型、调整 effect 中的派生状态和异步加载边界；仅当规则与框架当前官方约定确实冲突时，才允许最小范围豁免并说明原因。

备选方案是仅修复 error 并保留 warning。该方案无法完成“清账”，也会让后续新增 warning 难以区分，因此不采用。

### 2. 将质量流程拆成可组合脚本并提供单一聚合入口

在 `package.json` 中保留独立的 `lint`、`test`、`build`，新增明确的 `typecheck`，并增加按固定顺序执行静态检查、测试和生产构建的聚合命令。独立脚本便于快速定位，聚合入口则用于最终验收和自动化。

备选方案是只在 CI 工作流中硬编码命令。该方案会造成本地与 CI 行为漂移，因此不采用。

### 3. React effect 债务按状态来源重构

本地存储初值应尽可能通过惰性初始化或明确的客户端边界读取；异步请求的 loading 状态应由请求生命周期驱动，避免仅为启动请求而在 effect 顶层同步写状态。重构必须保持 SSR/水合安全，并保留取消过期请求或忽略过期响应的保护。

备选方案是逐行添加 `eslint-disable-next-line`。这只隐藏 React 19 检出的渲染级联风险，不解决根因，因此不采用。

### 4. 服务层 `any` 用领域类型和 Prisma 类型替代

快照与人员服务中的显式 `any` 应替换为现有领域模型、Prisma 生成类型、事务客户端类型或最小结构类型。类型收窄不得改变序列化格式、事务边界和恢复语义。

备选方案是使用 `unknown` 后立即断言回 `any`。这不提供真实类型保护，因此不采用。

### 5. 自动化只调用仓库质量入口

若仓库缺少 CI，则新增最小工作流，在干净安装后调用聚合质量命令；若已有等价自动化，则改为复用该入口。Node 版本和依赖安装方式应与项目锁文件保持一致，并避免在多个位置复制检查逻辑。

## Risks / Trade-offs

- [React 状态初始化调整可能产生水合差异] → 依据 Next.js 16 当前指南选择客户端安全初始化，并对本地存储缺失和已有值两种路径做验证。
- [effect 重构可能改变加载指示器时序] → 保留原有用户可见语义，并为搜索与设置数据加载补充针对性测试或可复现验证。
- [服务层类型收窄可能暴露潜在数据形状不一致] → 从 Prisma 与现有领域类型推导，先保持运行时逻辑不变，再逐步收窄。
- [生产构建依赖环境变量或外部服务] → 使用 `.env.example` 明确的构建期要求；无法离线满足的检查需记录原因，但不得把失败静默忽略。
- [统一质量命令耗时增加] → 保留可单独执行的快速脚本，聚合入口仅用于完整验收和 CI。

## Migration Plan

1. 阅读 Next.js 16 相关指南并记录适用于本次组件修改的约束。
2. 按文件修复 lint error，再清理全部 warning；每组修改后运行定向 lint 与相关测试。
3. 增加 `typecheck` 与聚合质量脚本，保证任一步失败都会返回非零退出码。
4. 补充必要回归测试和工程文档，并接入或更新 CI。
5. 依次执行 lint、类型检查、测试、生产构建，最终执行聚合命令留存验收结果。

本变更不涉及数据迁移。若出现行为回归，可回滚对应代码与脚本变更；数据库无需回滚。

## Open Questions

- 仓库目标 Git 托管平台若不是 GitHub，应在实施时将自动化步骤落到实际平台；质量脚本本身不受平台影响。
- 如果生产构建需要未纳入 `.env.example` 的必需变量，应先补齐示例和说明，再把构建纳入门禁。
