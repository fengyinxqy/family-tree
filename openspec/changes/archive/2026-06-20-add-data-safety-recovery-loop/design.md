## Context

当前 `Person`、`Relationship` 和 `PersonEvent` 以物理删除为主：删除人物会先删除事件和关系，再删除人物；删除关系也会立即移除记录。JSON 导入在校验后直接以事务清空并重建当前家谱。现有关系服务只检查重复边，AI 草稿应用和导入又各自拥有独立写入路径，因此完整性规则容易出现入口间不一致。

本变更横跨 Prisma 数据模型、人物与关系服务、AI 草稿应用、导入导出、树图/搜索/推理读取以及设置页。实现必须保持家谱空间隔离，并在同一事务中完成业务写入、家谱修订号更新和审计记录。

## Goals / Non-Goals

**Goals:**

- 让人物和关系删除可预览、可追溯、可恢复。
- 让所有业务读取默认忽略已删除记录。
- 让所有关系写入入口执行同一套图完整性规则。
- 让恢复导入和快照恢复遵循“预检—确认—执行前快照—原子写入”。
- 为并发变更提供明确的过期检测，避免按陈旧预览执行破坏性操作。
- 将任务拆成可独立验证、适合实现代理交接的步骤。

**Non-Goals:**

- 不提供任意字段编辑的一键撤销或完整事件溯源重放。
- 不实现多人角色权限、审核发布或实时协同。
- 不实现 GEDCOM、增量合并导入或跨家谱恢复。
- 不自动修复非法关系；系统只拒绝写入并返回可理解的原因。
- 不在本变更中引入定时清理任务或自动快照调度。

## Decisions

### 1. 使用软删除字段与删除操作批次，而不是把完整家谱复制到回收站

`Person` 和 `Relationship` 增加 `deletedAt`、`deletedBy`、`deletionOperationId`。删除人物时保留其 `PersonEvent`，并在一个事务中软删除人物以及所有当前有效的相邻关系；同一批记录共享删除操作 ID。业务查询通过统一的 active-record 查询帮助函数显式加入 `deletedAt: null`。

恢复人物时只恢复该人物删除批次连带删除的关系，并要求关系两端均为当前有效人物且不会违反完整性规则。事件无需复制或重建，人物恢复后重新可见。

选择该方案是因为它保留原始 ID 和引用，恢复成本低于序列化后重建。备选方案“每次删除创建全量快照”写放大明显，也难以恢复单个人物；“只依赖审计 JSON 反向写入”则更容易受模型演进影响。

### 2. 审计日志只追加，并与业务事务绑定

新增操作批次和审计条目模型。操作批次记录家谱、操作者、动作、状态、摘要和时间；审计条目记录实体类型、实体 ID、动作以及必要的变更前后 JSON。人物创建/更新/删除/恢复、关系创建/删除/恢复、导入与快照恢复均在业务事务中写入审计数据。

审计记录不向普通业务更新接口开放修改和删除。它用于解释和恢复，不作为构建当前状态的事件源。这样可以获得追溯能力，同时避免把现有 CRUD 架构一次性改造成 event sourcing。

### 3. 用家谱修订号绑定影响预览和破坏性确认

`FamilyTree` 增加单调递增的 `dataRevision`。所有会改变人物、事件、关系或恢复状态的事务必须同时递增修订号。删除影响预览、导入预检和快照恢复预检返回服务端保存的短期确认记录，其中包含家谱 ID、操作者、输入摘要哈希、基线修订号、操作类型和过期时间。

执行时服务端验证确认记录属于当前用户和家谱、尚未过期、输入哈希一致且 `dataRevision` 未改变；否则要求重新预检。确认记录必须一次性消费。

选择修订号而不是在执行时比较记录数量或时间戳，是因为关系目前没有 `updatedAt`，而数量也无法检测等量替换。代价是必须审计并更新所有写入入口，任务中将通过服务测试覆盖这一点。

### 4. 完整性校验实现为纯领域函数，并在事务写入前复用

新增不依赖 Next.js 或 Prisma 的家谱图校验模块。输入为当前有效人物、当前有效关系和候选变更，输出为结构化错误代码、相关人物/关系 ID 及用户可读说明。

规则至少包括：

- 任意关系两端不能是同一人物。
- 配偶关系按无向边判重；父母—子女关系按有向边判重。
- 新增父母—子女边后不能形成祖先环。
- 候选边不能与当前连通分量已经确定的代际差冲突；配偶同代、父母比子女高一代。

人物/关系表单、AI 草稿应用、导入预检及最终导入均调用同一验证器。最终写入必须在事务内基于最新数据再次验证，不能只相信客户端预检。

### 5. 快照复用版本化备份结构，但作为服务端受控记录保存

家谱快照保存当前版本化备份文档、创建原因（手动、导入前、恢复前）、创建者和创建时间。手动快照通过设置页创建；破坏性导入和快照恢复在执行事务前自动创建前置快照。

快照恢复不直接覆盖数据，而是复用导入预检和确认机制。恢复操作本身也会先创建快照，因此用户至少可以回到恢复前状态。用户下载的 JSON 备份继续只包含业务数据，不默认包含内部审计日志、确认记录或服务端快照。

### 6. 分阶段迁移读取路径

先迁移数据模型和共享查询/校验基础，再改写服务，最后启用 UI。所有树图、时间线、搜索、详情、AI 上下文、关系推理和导出读取都必须排除软删除记录。为防遗漏，除服务测试外，使用代码搜索清点直接访问 `person`、`relationship` 的查询，并为关键读取增加回归测试。

实现涉及 Next.js 页面、Server Actions 或 Route Handlers 前，实现代理必须先阅读 `node_modules/next/dist/docs/` 中对应 Next.js 16 指南和弃用说明。

## Risks / Trade-offs

- [遗漏 `deletedAt: null` 导致已删除数据重新出现] → 集中 active-record 查询帮助函数，清点所有直接查询，并覆盖树图、搜索、AI、推理和导出测试。
- [部分写入未递增 `dataRevision`，确认记录无法可靠失效] → 将修订递增封装进共享事务服务，并为每个写入入口增加 revision 断言测试。
- [并发写入在校验后形成非法图] → 在同一事务中读取最新有效图、执行最终校验和写入；必要时对家谱修订行加锁或使用可串行化事务及有限重试。
- [审计前后 JSON 包含敏感信息或快速膨胀] → 只记录恢复和解释所需字段，限制列表分页，不把密码、会话或 AI 密钥写入审计。
- [快照占用数据库空间] → 本阶段保留显式快照，不做高频自动调度；记录大小并为后续保留策略提供依据。
- [恢复旧关系与当前图冲突] → 恢复前重新运行完整性校验，冲突时保持全部数据不变并返回冲突明细。
- [旧代码仍执行物理删除] → 服务层移除公开物理删除入口，数据库级联仅保留给家谱空间永久删除等管理场景，并以集成测试验证。

## Migration Plan

1. 阅读相关 Next.js 16 与 Prisma 7 本地文档，确认 Server Action、Route Handler、事务和迁移约定。
2. 增加软删除、修订号、操作/审计、确认记录和快照模型；现有人物与关系的删除字段为空，家谱修订号从 `0` 开始。
3. 实现 active-record 查询帮助函数、图完整性验证器、修订号与审计事务基础，并先完成单元测试。
4. 迁移人物、关系、事件更新和 AI 草稿应用写入；再迁移所有读取路径。
5. 增加删除影响预览、回收恢复、操作记录和手动快照服务及 UI。
6. 增加导入/快照恢复预检、一次性确认和自动前置快照，保留现有原子事务保证。
7. 运行 Prisma 迁移、测试、ESLint 和生产构建，并手工验证跨家谱隔离、陈旧确认拒绝及恢复冲突。

回滚时先回退应用到仍兼容新增可空字段的版本；新增表和字段暂不删除，避免丢失审计与恢复数据。确认无需恢复后，再通过独立迁移清理。

## Open Questions

- 服务端快照的长期保留数量和存储上限留到获得真实数据规模后决定；本变更只提供手动和破坏性操作前快照，不自动清理。
- 审计日志未来是否对协作成员全部开放，将由 V1.4 权限模型决定；本变更仅允许当前家谱所有者访问。
