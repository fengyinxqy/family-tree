## Context

当前 `unified-agent.ts` 在一次 HTTP 请求中向模型发送用户消息，最多执行第一个工具调用，再以 `tool_choice=none` 生成最终答复。服务端不保存对话、计划、运行状态或工具轨迹，前端刷新后上下文消失，也无法在用户澄清、请求中断或工具失败后恢复。现有工具实现同时承担模型工具描述、业务查询和响应拼装，继续横向增加 OCR、资料引用、人物事件等工具会放大耦合。

项目已经具备家谱权限、完整性校验、不可变修订组、审校发布、来源追溯和审计能力。新的 Agent 必须利用这些边界，而不能另建一条绕过正式工作流的写入路径。后续 OCR 会带来多模态输入、长耗时工具、来源定位和置信度，因此运行时需要从一开始支持持久状态、人工中断和可追踪工具结果。

## Goals / Non-Goals

**Goals:**

- 使用 LangChain JS 统一模型、消息、工具、结构化输出和提供方适配。
- 使用 LangGraph 将 Agent 表达为有界、可持久化、可中断恢复的状态图。
- 持久化产品级会话、运行、消息、步骤和工具审计，并在服务重启或用户补充信息后恢复。
- 对每次运行强制执行轮次、工具调用、耗时和上下文预算。
- 让只读调查可以自主执行，而任何正式数据变化只能产出修订组并进入人工审校发布流程。
- 交付首个资料补全 Agent，并为未来 OCR/多模态工具保留稳定扩展点。

**Non-Goals:**

- 本变更不实现 OCR 引擎、向量检索、RAG 或资料自动切片。
- 不实现无人值守后台长任务、定时任务或多 Agent 协作。
- 不允许 Agent 自动批准、发布、撤回或直接修改正式家谱数据。
- 不在第一阶段迁移所有既有专用 Agent API；旧入口可通过适配器逐步收敛。
- 不把 LangSmith 或其他托管观测平台设为运行必需条件。

## Decisions

### 1. 采用 LangChain JS + LangGraph，而不是手写递归工具循环

引入 `@langchain/core`、`@langchain/langgraph` 和匹配当前模型提供方的 LangChain 适配包。LangChain 负责标准消息、工具模式、结构化输出与模型调用；LangGraph 负责状态节点、条件边、检查点、中断和恢复。运行图至少包含：加载上下文、模型决策、执行工具、评估预算、请求人工介入、形成结果和结束。

选择它的主要原因不是减少几行循环代码，而是后续 OCR 会增加长耗时工具、多模态消息、失败重试和人工校正节点，状态图比隐藏在控制器中的递归更容易检查和演进。备选方案是继续扩展当前自研循环；依赖更少，但暂停恢复、检查点和状态迁移都需要自行维护，因此不采用。

业务规则不得写进 LangChain/LangGraph 节点的匿名闭包。领域工具、预算策略和修订组服务保持独立接口，以避免框架锁定。若未来替换编排框架，正式数据和权限边界不受影响。

### 2. LangGraph 检查点与产品级运行记录分层保存

LangGraph 使用 PostgreSQL 持久化检查点，`thread_id` 绑定产品侧 `AgentSession.id`，用于恢复图状态。应用数据库同时新增产品级实体：

- `AgentSession`：所属家谱、创建者、Agent 类型、标题、状态、当前运行及时间戳。
- `AgentMessage`：用户、助手、系统摘要或工具可见消息，包含顺序和安全元数据。
- `AgentRun`：目标、状态、预算快照、模型、提示词版本、开始/结束原因和错误分类。
- `AgentStep`：节点、序号、输入输出摘要、耗时、Token 与关联工具调用。
- `AgentToolCall`：工具名、模式版本、参数摘要、权限决策、状态、幂等键和结果摘要。

检查点是运行恢复机制，不作为产品审计或 UI 查询的唯一来源；产品实体是可授权、可检索和可保留的业务记录。每个图步骤使用稳定的运行/步骤标识写入，重放时通过幂等键避免重复副作用。检查点与审计记录短暂不一致时，运行进入可重试失败状态，并由恢复逻辑从最后完整步骤继续。

### 3. 工具注册表显式声明权限和副作用等级

每个工具通过统一注册表提供名称、版本、用途、Zod 输入输出模式、超时、权限动作和副作用等级：

- `READ`：查询人物、关系、资料、缺口或确定性推理，可在授权和预算内自主调用。
- `PROPOSE`：创建或更新 Agent 工作产物、草稿或不可变修订组，必须在图中经过确认节点。
- `FORBIDDEN`：发布、批准、撤回、成员管理、删除等能力不向 Agent 注册。

每次工具执行前重新解析会话所属家谱与当前用户权限，禁止依赖模型传入的 `treeId`、用户 ID 或对象存储键。参数和结果必须经过模式校验；日志只保存安全摘要，敏感正文和文件内容不得原样写入审计字段。

未来 OCR 工具应以已授权的 `materialId`/`mediaObjectId` 为输入，由服务端获取文件并返回带页码、区域或文本片段定位、置信度和模型版本的结构化结果。这样 OCR 是新增工具和节点，而不是改变运行时协议。

### 4. 使用硬性预算和确定的终止原因约束自主性

每次运行在开始时固化预算快照，包括最大模型轮次、最大工具调用数、单工具及总耗时、最大失败重试次数和上下文上限。每个模型节点和工具节点之后都进入预算检查节点。达到边界时不得继续调用模型，运行以 `BUDGET_EXHAUSTED` 停止并给出已完成工作和继续选项。

同一会话最多有一个活动运行。支持的终止或暂停状态至少包括 `COMPLETED`、`WAITING_FOR_USER`、`WAITING_FOR_CONFIRMATION`、`FAILED`、`CANCELLED` 和 `BUDGET_EXHAUSTED`。用户回复只恢复明确等待用户的运行；普通新目标创建新运行，避免把无关指令混入旧检查点。

### 5. 人工介入是图中的一等状态

当身份匹配不唯一、关系方向不明、证据不足、即将执行 `PROPOSE` 工具或模型请求超出授权时，图必须中断并持久化结构化的 `AgentInterruption`：原因、问题、可选项、待执行动作摘要和恢复模式。客户端展示该状态，用户的回答或确认经服务端校验后作为恢复命令写入，而不是拼接为不可区分的普通聊天文本。

确认与实际执行绑定同一工具名、参数哈希、家谱修订号和过期时间；任何一项变化都必须重新确认。该模式复用现有确认与修订基础，不把“用户说了可以”当作永久授权。

### 6. 首个资料补全 Agent 只调查并形成受控产物

资料补全图接收人物或分支范围，先解析目标，再调用只读工具收集人物、关系、事件、资料引用和完整性信息。它应区分“数据库中缺失”“来源中未发现”和“存在冲突”，只提出会改变后续判断的少量问题。

结束产物有两类：无需写入时生成带证据摘要的缺口报告；用户补充了可结构化事实时生成现有格式的录入草稿，并在用户确认后通过既有服务创建不可变修订组。Agent 不直接创建 Person、Relationship 或 PersonEvent，也不调用审校或发布操作。

### 7. API 使用命令与事件协议，保留流式体验

新增会话创建/查询、运行启动、运行恢复和取消接口。流式响应使用稳定事件类型传递文本增量、步骤状态、工具状态、人工介入、产物和终止原因；数据库是最终状态来源，断线重连后客户端先拉取已持久化状态，再订阅后续事件。

第一阶段运行仍由请求触发并设置较短硬超时，不引入任务队列。持久化检查点保证失败后可显式恢复，但不承诺请求断开后继续后台执行。OCR 等长任务落地前，再基于同一 `AgentRun` 协议接入队列工作器。

### 8. 模型适配、提示词和状态版本必须可追踪

LangChain 模型工厂读取现有 OpenAI/DeepSeek 配置并返回统一 ChatModel，不允许业务节点直接实例化提供方客户端。每次运行记录提供方、模型名、提示词版本、图版本、工具模式版本和预算。图状态带显式版本，部署新版本时仅恢复兼容检查点；不兼容运行标记为需要重新开始，并保留历史记录。

## Risks / Trade-offs

- [LangChain/LangGraph API 演进较快] → 固定精确依赖版本，集中封装模型、工具和检查点适配器，并以契约测试覆盖升级边界。
- [检查点与产品审计双写可能短暂不一致] → 使用稳定步骤 ID、幂等写入和恢复校验；任何不完整步骤不得执行提案级副作用。
- [多步 Agent 增加延迟和模型成本] → 默认小预算、确定性工具优先、上下文摘要和按步骤用量记录。
- [模型可能循环调用或选择错误工具] → 图级预算、工具白名单、结构化输出校验和失败熔断共同终止异常运行。
- [恢复旧检查点可能与新代码不兼容] → 版本化图状态、提示词和工具模式，不兼容时只读展示并要求新建运行。
- [未来 OCR 结果体积大且含敏感信息] → 工具仅返回受限结构化片段与定位，原文件留在授权存储中，日志不保存全文。
- [请求内执行无法承载长 OCR] → 第一阶段明确限制短任务；后续队列工作器复用相同会话、运行和检查点协议。

## Migration Plan

1. 实现并迁移 Agent 产品实体，同时部署 LangGraph PostgreSQL 检查点存储；不改动现有正式家谱表。
2. 引入 LangChain 模型工厂和工具注册表，以契约测试验证 OpenAI/DeepSeek、权限、模式校验和审计摘要。
3. 实现最小状态图、预算、人工中断、恢复和取消，并用测试模型覆盖循环、失败和重放。
4. 将现有人物查询、关系推理、缺口分析和录入草稿包装为新工具；旧 API 暂时保留。
5. 上线资料补全 Agent 与新版流式事件客户端，先通过功能开关限制到受控用户。
6. 验证运行记录、修订组隔离和故障恢复后，再决定是否让 `/api/agent/chat` 默认进入新运行时。

回滚时关闭功能开关并恢复旧聊天入口；新增 Agent 表和检查点保留为只读审计数据，不删除、不影响现有修订和正式业务记录。

## Open Questions

- OCR 引入时采用应用内队列还是独立工作器，将在 OCR change 中根据文件规模和延迟目标决定。
- Agent 会话与运行记录的保留期、用户导出和清理策略需要在正式上线前与隐私策略一起确定。
- 是否接入 LangSmith 仅作为可选开发观测能力，待本地审计指标稳定后再评估。
