## Context

应用目前只有 `/documents` 占位页，持久化数据集中在人物、关系、事件及数据安全模型。V1.3 需要让扫描件、照片、PDF 和整理材料进入家谱，并成为后续 OCR 与结构化信息的可追溯来源。该能力横跨数据库、私有文件存储、授权 API、人物详情、导入导出和恢复机制。

实现代理在修改任何 Next.js 页面、路由或服务代码前，必须先阅读 `node_modules/next/dist/docs/` 中与 Route Handlers、请求体/表单上传、缓存和鉴权相关的当前版本指南。

## Goals / Non-Goals

**Goals:**

- 建立家谱范围内统一的资料条目、文件对象和目标关联模型。
- 允许用户上传受支持文件，维护资料元数据，并关联人物、人物事件或整棵家谱。
- 通过服务器授权后的流式响应访问私有文件，不向客户端暴露可长期复用的存储地址。
- 将资料纳入人物详情、审计、软删除、快照、恢复和家谱交换包。
- 为后续 OCR 保存稳定的资料、文件和来源标识，但不预设 OCR 数据结构。

**Non-Goals:**

- OCR、版面分析、AI 候选提取和人工审校草稿。
- 缩略图转码、图片编辑、视频/音频处理和全文搜索。
- 家族成员角色、协作审校、公开发布和外链分享。
- 通用数字资产管理系统、文件夹层级或复杂标签体系。

## Decisions

### 1. 条目、文件与关联分层建模

新增 `SourceMaterial` 作为可描述和引用的业务条目，新增 `MediaObject` 保存文件元数据与存储键，新增 `MaterialLink` 表示条目到人物或人物事件的关联。资料条目天然属于一棵 `FamilyTree`；没有目标关联时即代表家谱级资料。

`SourceMaterial` 保存标题、类别、来源、年代文本、提供者、说明、创建者与软删除字段。`MediaObject` 保存原始文件名、MIME 类型、字节数、内容哈希、存储键和创建时间。`MaterialLink` 使用明确的可空 `personId` / `personEventId` 外键，并以数据库约束或事务校验保证每行恰好一个目标。

选择分层模型而不是把文件字段直接放在资料条目上，是为了支持一份资料包含多页扫描件，同时让后续 OCR 能精确引用某个文件。选择显式外键而不是通用 `targetType + targetId`，是为了获得数据库级引用完整性。

### 2. 文件本体使用可替换的私有对象存储适配器

业务数据库只保存文件元数据、内容哈希和不可猜测的 `storageKey`；文件字节由 `src/lib/storage` 下的服务端接口管理。首个实现提供受配置约束的本地私有目录适配器，目录必须位于 `public/` 之外；部署环境可在保持接口不变的情况下接入持久对象存储。

上传采用“先校验、写临时对象、提交数据库、再确认对象”的补偿式流程；数据库失败时删除临时对象，删除资料时先软删除数据库记录，物理清理延后执行。相比把二进制写入 PostgreSQL，该方案避免备份和查询膨胀；相比直接公开对象 URL，它保留统一授权边界。

### 3. 服务器端集中校验上传与访问

允许的首批 MIME 类型为 PDF、JPEG、PNG、WebP 和 TIFF；允许列表、单文件大小和单条目文件数由服务端常量统一控制。服务端不得信任浏览器提供的文件名或 MIME 类型，必须规范化文件名、检查文件签名、计算 SHA-256，并拒绝空文件、超限文件和不一致类型。

文件读取路由根据 `MediaObject -> SourceMaterial -> FamilyTree` 解析归属并复用当前家谱访问校验，然后流式返回内容，设置安全的 `Content-Type`、`Content-Disposition`、`X-Content-Type-Options: nosniff` 和私有缓存策略。列表和详情响应不返回物理路径或存储凭据。

### 4. 资料变更复用现有数据安全边界

资料条目采用软删除；删除条目会在同一事务中隐藏其关联和文件元数据，并写入一个操作批次。物理文件不在业务事务中立即删除，以保证恢复窗口。创建、编辑、关联、删除和恢复均递增家谱 revision 并写不可变审计记录。

快照保存资料条目、文件元数据和关联，不复制文件字节。恢复前验证快照引用的对象仍存在；缺失对象形成阻断性冲突，避免恢复出不可读资料。人物被软删除时，资料条目保持存在，但指向该人物的关联不在普通读取中显示。

### 5. 交换包使用清单加文件载荷

现有纯 JSON 备份升级为版本化 ZIP 交换包：根目录包含 JSON 清单，文件载荷位于固定的 `files/` 路径。清单用稳定导出 ID 和 SHA-256 引用文件，禁止使用数据库 ID、绝对路径或原始存储键。导入预检校验 ZIP 路径、总解压大小、文件数量、哈希、MIME 类型和所有引用，然后沿用 revision-bound confirmation 执行原子业务恢复与补偿式对象写入。

不继续把二进制嵌入 JSON/base64，因为体积膨胀明显且难以流式处理。旧 JSON 格式继续作为可导入版本保留；新导出默认生成包含资料的新版交换包。

### 6. 页面按资料管理与上下文展示拆分

`/documents` 提供家谱内资料列表、筛选、创建/编辑、上传和详情入口；人物详情仅展示与当前人物直接关联的资料摘要，并链接到资料详情。前端展示只消费授权 API 返回的领域 DTO，不拼接存储路径。

## Risks / Trade-offs

- [对象存储与数据库无法共享事务] → 使用临时对象、补偿删除、内容哈希和孤儿清理任务，并覆盖失败路径测试。
- [本地文件存储不适合无状态生产部署] → 将存储接口作为强边界；生产发布前必须配置持久适配器，本地适配器仅用于开发和单机部署。
- [ZIP 导入存在路径穿越或解压炸弹风险] → 拒绝绝对路径和 `..`，限制文件数、单文件大小与总展开大小，并在写入前完成清单和哈希校验。
- [软删除文件长期占用空间] → 本变更保留恢复优先策略，后续提供基于保留期且可审计的垃圾回收任务。
- [多态关联约束复杂] → 首版仅支持人物和人物事件的显式外键，并在数据库与服务层同时保证单一目标。

## Migration Plan

1. 阅读 Next.js 16 对应指南并确认当前路由、缓存和上传约束。
2. 增加 Prisma 模型、索引与迁移；现有家谱数据无需回填。
3. 实现存储接口、本地私有适配器、上传校验和失败补偿测试。
4. 实现资料服务与授权 API，再接入 `/documents` 和人物详情。
5. 扩展审计、快照和恢复，验证删除与恢复的原子性。
6. 升级交换包格式，并保留旧 JSON 导入兼容测试。
7. 依次运行定向测试、`npm run lint`、`npm run typecheck`、`npm test` 和 `npm run build`。

回滚时先停止新上传，再回滚应用代码；数据库新增表可暂时保留以避免资料丢失。对象文件不得随应用回滚而删除。只有确认不存在需保留资料后，才能单独执行破坏性数据库回滚与对象清理。

## Open Questions

- 生产环境最终采用哪一种持久对象存储，由部署环境在实现前确认；本设计不把领域模型绑定到具体供应商。
- 物理文件的保留期与垃圾回收策略留待数据保留政策确定后另行提案。
