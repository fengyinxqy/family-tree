## Context

当前关系问答链路由两部分组成：LLM 只负责从自然语言问题中提取两个人名，真正的亲属关系计算由 `src/lib/kinship/relationship-engine.ts` 中的确定性 TypeScript 引擎完成。现有引擎已经能通过 BFS 找到最短路径，并对少量固定路径模式输出中文称谓，但对伯、叔、姑、姨、舅、侄、甥、堂、表等常见旁系关系仍覆盖不足，很多结果会退化成笼统的兜底描述。

当前实现还有几个现实约束：
- 数据模型只有 `spouse` 和 `child` 两类原始关系，所有中文亲属称谓都必须从 hop 序列推导，而不是直接存库
- 当前推理深度上限为 5，新增称谓规则应优先围绕三代内、短路径、高频关系展开
- 关系问答结果会同时展示 `relationship`、`inverseRelationship` 和 `explanation`，因此命名规则需要兼顾正向、逆向和解释文案一致性
- 仓库已有轻量测试模式，使用 `node:test` + `npx tsx <file>` 运行单文件测试，适合为关系引擎补回归样例

## Goals / Non-Goals

**Goals:**
- 提升三代内常见旁系关系的中文称谓覆盖率
- 为同一条路径同时返回更自然的正向称谓和逆向称谓
- 保留并强化推理解释，让用户能看懂称谓从哪条路径得来
- 将无法精确命名的路径收敛到更友好的分层兜底文案，而不是统一落回单一句子
- 为新增路径模式建立可回归的单元测试样例

**Non-Goals:**
- 不扩展底层关系模型，仍基于 `spouse` / `child` 推导
- 不追求一次覆盖所有中国地域、宗族、长幼、婚配场景下的全部细分称谓
- 不引入按年龄排序、排行字段、嫡庶或父系/母系绝对判定等当前数据模型不具备的信息
- 不改动 LLM 问题解析协议或人物匹配逻辑

## Decisions

### D1: 继续采用“路径模式 -> 中文称谓”规则映射，而不是引入通用规则求解器

**选择**: 在现有 `describePath()` 基础上继续扩展固定路径模式映射，优先补齐高频模式及其正反向称谓。

**原因**:
- 当前引擎已经是按 `pattern === "parent>child>child"` 这类形式工作，局部扩展成本最低
- 项目数据维度有限，暂时没有足够结构信息支撑一个更抽象的亲属规则系统
- 路径模式可直接和单元测试一一对应，便于快速迭代

**备选方案**: 引入通用 kinship rule engine，根据代际、旁系/直系、父系/母系动态组合称谓。
- 拒绝理由：实现复杂度明显更高，且现有数据缺少年龄顺序、父系/母系确定性等信息，短期内容易做出看似通用但实际错误率更高的系统。

### D2: 将新增称谓分成“精确命名层”和“友好兜底层”

**选择**: 对高置信路径输出精确中文称谓；对路径已知但信息不足以精确命名的情况，输出比当前更具体的过渡文案。

建议分层：
1. **精确命名层**：可稳定映射到伯叔姑姨舅、侄甥、堂表亲等
2. **半精确层**：可确定属于“父母辈旁系长辈”“同辈旁系亲属”“姻亲长辈/晚辈”
3. **兜底层**：仍保留路径说明，但避免只说“存在可解释的亲属路径”

**备选方案**: 所有未覆盖路径继续沿用统一兜底句式。
- 拒绝理由：这正是当前用户感知最差的地方，路径虽然算出来了，但结果看起来像“系统不会说人话”。

### D3: 逆向称谓单独定义，不依赖简单字符串反转

**选择**: 每条新增规则显式给出 `relationship` 和 `inverseRelationship`，必要时分别命名。

**原因**:
- 中文亲属称谓不是简单对称的，例如“侄女”的逆向是“姑/姨/伯叔舅辈长辈”之一，而不是一个机械反向词
- 当前引擎 API 已经支持同时返回 `relationship` 和 `inverseRelationship`
- 显式定义更容易在测试里固定预期，减少误解

**备选方案**: 只维护正向称谓，逆向一律复用或用泛化文案。
- 拒绝理由：这会让同一条路径在 UI 上看起来前后一致性不足，也浪费了现有结果结构。

### D4: 在当前数据能力范围内，优先利用目标性别与分支人物性别，不依赖长幼信息

**选择**: 延续当前实现里基于目标人物性别、分支人物性别的命名方式，输出“伯叔”“姑姨”“堂表兄弟姐妹”这类聚合称谓，而不是强行细分“伯/叔”“哥/弟”“姐/妹”。

**原因**:
- 当前没有可靠的出生序、排行或年龄比较逻辑，无法稳定区分长幼
- 聚合称谓虽然不够极致精细，但显著优于完全兜底，且不容易误导

**备选方案**: 通过 birthDate 或创建顺序推测长幼，输出更细称谓。
- 拒绝理由：当前数据完整度不足，推测长幼会引入“看起来很准、实际很错”的问题。

### D5: 为关系引擎补专用回归测试文件

**选择**: 在 `src/lib/kinship/__tests__/` 下新增关系引擎测试，用 `node:test` + `tsx` 与现有 agent 测试风格保持一致。

**原因**:
- 当前仓库已经在 agent 模块采用这一轻量模式
- 关系路径与称谓映射是典型纯函数逻辑，最适合用表驱动样例测试
- 这类变更很容易在后续增量规则中互相覆盖，测试价值高

**备选方案**: 仅手工在页面上验证关系问答结果。
- 拒绝理由：人工回归难以覆盖多种 hop pattern，后续每次补规则都容易回退已有称谓。

## Risks / Trade-offs

- **[称谓精度受数据上限限制]** → 明确采用聚合称谓，如“伯叔”“姑姨”“堂表亲”，避免伪精确
- **[新增规则可能与现有最短路径命中顺序冲突]** → 先梳理当前 pattern 优先级，并用表驱动测试锁定行为
- **[路径存在多种可解释称谓]** → 优先输出当前数据条件下最稳妥的中性中文称谓，并在 explanation 中说明路径来源
- **[规则继续堆叠会让 describePath 变长]** → 将新增 pattern 整理成更清晰的命名分组或映射辅助函数，避免后续维护失控

## Migration Plan

- 本次变更不涉及数据库 schema、存量数据迁移或外部接口协议变更
- 可按普通应用发布上线
- 如发现新增命名规则引入错误，可回退到上一版 relationship-engine.ts 与对应测试文件
