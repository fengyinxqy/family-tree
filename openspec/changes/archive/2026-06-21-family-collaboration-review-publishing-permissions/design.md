## Context

当前系统以 `FamilyTree.ownerId` 和业务记录的 `createdBy` 作为主要数据隔离条件，页面与服务通常假定登录用户就是家族所有者。人物、关系、事件和文献媒体直接写入正式业务表；系统已有 `dataRevision`、操作批次、审计条目、确认令牌和快照能力，但没有成员关系、角色授权、草稿修订或发布边界。

本变更横跨身份授权、数据模型、所有写入口、读取可见性、审计和协作界面。实现代理在修改 Next.js 代码前必须先读取 `node_modules/next/dist/docs/` 中与路由处理器、服务端组件、缓存和变更操作相关的当前版本指南。

## Goals / Non-Goals

**Goals:**

- 以家族成员关系而非记录创建者作为家族作用域访问依据。
- 提供可测试、服务端强制执行的预设角色与权限矩阵。
- 通过不可变修订实现草稿、审校和发布，确保未发布内容不进入正式读取与导出。
- 让发布操作复用现有完整性校验、事务、数据版本和审计基础设施。
- 提供可迁移、可回滚的实施顺序，并保持现有所有者数据可访问。

**Non-Goals:**

- 首期不提供用户自定义角色或逐记录 ACL。
- 首期不提供多人实时协同编辑、字段级合并或 WebSocket 在线状态。
- 首期不建设公共搜索、SEO 门户或匿名评论系统。
- 不允许审校流程绕过现有家谱完整性、文件安全、删除确认和恢复规则。

## Decisions

### 1. 以显式成员关系和固定角色作为授权来源

新增 `FamilyMembership`，以 `(treeId, userId)` 唯一标识成员，保存 `OWNER`、`ADMIN`、`EDITOR`、`REVIEWER`、`VIEWER` 角色及 `ACTIVE`、`SUSPENDED` 状态；新增带哈希令牌、目标邮箱、目标角色、有效期和使用状态的 `FamilyInvitation`。所有者同时保留 `FamilyTree.ownerId` 作为不可歧义的最终所有权来源，并存在一条对应的 OWNER 成员记录。

权限通过集中式 `authorizeFamilyAction(userId, treeId, action)` 服务解析，路由、服务和服务端页面不得自行散落角色判断。预设能力为：OWNER 拥有全部能力；ADMIN 可管理非所有者成员并编辑、审校、发布；EDITOR 可创建修订并提交；REVIEWER 可查看工作区并审校他人修订；VIEWER 仅查看已发布内容。恢复、快照恢复、所有权转移仅限 OWNER。

选择固定角色而非自定义 RBAC，是为了让首期权限可解释、可穷举测试且迁移简单。代价是灵活性较低，未来可在集中式 action 层扩展而不改调用方。

### 2. 邀请接受必须绑定身份且一次性消费

邀请明文令牌只在创建时返回，数据库仅保存哈希。接受时必须登录且登录邮箱与邀请目标邮箱规范化后一致；令牌过期、撤销、已使用或家族已存在成员时均拒绝。接受邀请与创建成员记录、标记邀请已使用、写审计必须在同一事务完成。

相比可转发的通用邀请链接，邮箱绑定减少误加入和权限外泄；后续若需要开放邀请，可新增独立邀请类型。

### 3. 使用不可变内容修订承载协作状态

新增 `ContentRevision`，记录家族、内容类型、目标实体、基线 `dataRevision`、作者、状态、结构化 payload、提交时间和版本号；新增 `ReviewDecision` 保存审校者、结论、意见和时间；发布信息保存发布者、发布时间及发布操作批次。

业务编辑不直接修改人物、关系、事件和文献媒体正式表，而是创建或更新作者当前的 DRAFT 修订。提交后修订不可变；退回后通过派生新版本继续修改，保留完整历史。对新建内容，目标实体可为空并在发布时创建；对已有内容，修订 payload 保存发布所需的完整候选状态。

选择统一修订表而非为每种业务实体建立一套草稿表，可统一状态机、权限、队列和审计。JSON payload 降低跨实体扩展成本，但必须使用按内容类型区分的 Zod schema 做运行时验证，禁止无类型 payload 直接进入发布事务。

### 4. 发布是唯一写入正式业务表的协作路径

发布服务在单一数据库事务中重新验证发布权限、修订状态、基线版本、payload schema、家族作用域及领域完整性；随后写入正式业务表、递增 `FamilyTree.dataRevision`、标记修订已发布并写操作批次与审计条目。任一步失败必须整体回滚。

现有家谱页面、详情、导出和公开读取继续查询正式业务表，因此天然只看到已发布数据。工作区读取在正式版本之上额外加载当前用户可见的草稿、待审和审校信息，不把草稿混入普通领域查询。

相比让正式表保存 `draft/published` 状态，此方案避免所有现有查询都增加状态过滤，也降低草稿关系参与家谱推导的风险。代价是发布服务需要为各内容类型实现 payload 到领域写入的适配器。

### 5. 采用严格状态机与职责分离

允许的主状态迁移为 `DRAFT → IN_REVIEW → APPROVED → PUBLISHED`，审校退回为 `IN_REVIEW → CHANGES_REQUESTED`，作者从退回修订派生新 `DRAFT`。发布前允许具备发布权限的用户取消已通过状态并退回，但已发布修订不可原地修改。

REVIEWER 不得审校自己的修订；OWNER 或 ADMIN 可在紧急情况下审校自己提交的修订，但系统必须要求填写原因并写入审计。默认 UI 不提供该快捷路径，避免常态化自批。

### 6. 以乐观并发和领域校验阻止过期发布

修订保存基线 `dataRevision` 与目标实体版本信息。发布时若家族版本已变化，不一概拒绝：系统先判断变化是否涉及修订目标或其完整性依赖；无关变化可继续，相关变化则返回结构化冲突并要求基于最新正式数据派生新草稿。关系、人物关键字段和批量内容发布必须在事务内复用最新家谱完整性校验。

这比全局版本变化即拒绝减少无关冲突，同时比最后写入覆盖更安全。首期不做自动字段合并。

### 7. 成员与协作事件进入现有不可变审计体系

邀请创建/撤销/接受、成员停用/移除、角色变更、修订提交、审校决定和发布均创建 `OperationBatch` 与 `AuditEntry`。审计摘要只保存必要标识、角色变化和修订元数据，不保存邀请明文令牌、密码、文件字节或敏感备注全文。产品不提供直接撤回已发布内容的入口；发布后的更正必须从当前正式状态派生新修订并重新审校发布。

## Risks / Trade-offs

- [现有查询按 `createdBy` 限制，成员加入后可能仍看不到数据] → 分阶段将所有家族作用域查询改为先授权成员、再仅按 `treeId` 过滤，并用回归测试扫描残留模式。
- [统一 JSON 修订可能出现类型漂移] → 为每种内容类型建立版本化 schema、解析器和发布适配器，持久化 schema 版本并拒绝未知版本。
- [发布时家族版本频繁变化导致冲突] → 检测目标及依赖范围，返回可操作冲突详情，允许从最新正式版本派生草稿。
- [管理员权限过大造成误操作] → 恢复、快照恢复和所有权转移保持 OWNER-only，成员管理和发布均审计。
- [历史正式数据没有修订记录] → 将其视为基线版本，不回填伪造审校历史；首次修改时创建修订。
- [状态机增加产品复杂度] → 使用固定角色、单一待审队列和明确中文状态提示，首期不加入自定义流程。

## Migration Plan

1. 阅读本仓库 Next.js 16 相关指南，确认服务端授权、路由和缓存实现方式。
2. 添加成员、邀请、修订和审校数据模型及索引；迁移时为每个家族所有者创建 OWNER 成员记录。
3. 实现集中式授权服务和权限矩阵，先覆盖读取入口，再覆盖所有写入口；补齐跨家族与停用成员测试。
4. 将业务查询从 `createdBy + treeId` 迁移为授权后的 `treeId` 作用域，保持正式数据行为不变。
5. 实现邀请和成员管理 API、事务审计及设置界面。
6. 实现修订 schema、状态机、待审队列和审校服务，暂不切换现有写入口。
7. 为各内容类型实现发布适配器，接入完整性校验、版本递增和审计；以人物/事件、关系、文献媒体的顺序逐类切换写入口。
8. 最后切换导入和 AI 草稿应用到修订提交流程，验证未发布内容不会进入普通读取、导出、快照或公开展示。
9. 运行定向测试、类型检查、lint、完整测试与生产构建；执行权限矩阵和并发发布的端到端验证。

回滚时先关闭邀请、审校和发布入口，再将仍未发布的修订保留为只读历史；正式业务表始终保存最后成功发布状态，可回退应用代码。若需回退数据库结构，应先导出成员与修订审计数据，且不得删除已发布操作对应的审计记录。

## Open Questions

- 首期是否开放匿名公开访问，还是仅区分“成员已发布”与“工作区草稿”；规格按前者可配置、默认关闭处理。
- ADMIN 是否应获得手工快照创建权限；当前设计为 OWNER-only，以保持恢复边界最保守。
- 发布通知首期采用站内队列还是仅界面状态提示；本变更要求可见状态，不强制外部邮件或即时消息。
