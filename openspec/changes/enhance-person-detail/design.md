## Context

当前人物详情页的数据来源主要是 `Person` 基础字段和 `Relationship` 关系表。页面会在服务端一次性查询人物与双向关系，然后把配偶、父母、子女拆成三个列表展示；编辑入口仍复用基础人物表单，只支持 `name`、`gender`、`birthDate`、`deathDate`、`bio` 这些 MVP 级字段。

“人物详情增强”会同时影响数据库模型、API 返回结构、表单校验和详情页呈现：
- `Person` 需要承载更多档案字段
- 人生事件需要按人物维度存储并可排序展示
- 关系摘要需要从现有关系记录中派生，而不是新增冗余表

当前实现还有几个约束：
- 项目使用 Prisma + PostgreSQL，当前日期字段以字符串形式存储，新增方案需要兼容这一现实而不是顺手重做整套日期模型
- 详情页和编辑页直接依赖 Prisma 查询结果，若返回结构变化过大，页面和 API 都要同步调整
- 现有数据只有 `spouse` / `child` 两类原始关系，关系摘要应继续基于推导和分组来生成

## Goals / Non-Goals

**Goals:**
- 让人物档案可表达别名、排行、籍贯和备注等补充信息
- 为人物提供可增删改查的事件时间线，至少覆盖出生、婚姻、迁徙、离世等高频类型
- 在人物详情页提供更易扫读的关系摘要，而不只是三个平铺列表
- 让新增字段和事件能力在详情页、编辑页、API 和服务层保持一致

**Non-Goals:**
- 不重构现有 `birthDate` / `deathDate` 字段为真正的 `DateTime`
- 不引入文件上传、照片资料绑定或资料中心能力
- 不改造关系模型本身，也不在本轮处理重复人物合并、关系纠错等脏数据治理
- 不建设跨人物、跨家族的全局时间线视图

## Decisions

### D1: 扩展 `Person` 标量字段承载档案信息，事件使用独立 `PersonEvent` 表

**选择**:
- 在 `Person` 上新增 `aliases: String[]`、`generationLabel`、`nativePlace`、`notes` 等可选字段
- 新增 `PersonEvent` 模型，包含 `personId`、`type`、`title`、`dateLabel`、`location`、`description`、`sortOrder` 等字段

**原因**:
- 档案字段属于人物静态属性，放在 `Person` 上最直接，查询与编辑成本最低
- 人生事件是一对多结构，单独建表更适合排序、扩展和后续时间线能力
- `aliases: String[]` 能避免为少量别名单独建表，同时比逗号拼接字符串更稳定

**备选方案**: 所有扩展信息都放进一个 JSON 字段。
- 拒绝理由：会削弱表单校验、类型提示和 Prisma 查询可维护性，也不利于后续按事件类型过滤。

### D2: 保留 `birthDate` / `deathDate` 作为人物基础字段，并在详情页时间线中合成展示

**选择**:
- 出生与离世继续使用现有 `Person.birthDate` / `Person.deathDate`
- 详情页渲染时间线时，把这两个字段映射为只读系统事件，与 `PersonEvent` 记录一起按时间顺序输出
- 不允许用户同时在 `PersonEvent` 中再创建重复的 `birth` / `death` 事件记录

**原因**:
- 这样可以避免一次变更同时迁移旧数据和旧表单
- 保持对现有新增/编辑人物链路的兼容，降低 schema 变更风险
- 用户能在同一个时间线区域看到完整人生节点，但底层数据不需要双写

**备选方案**: 将出生和离世也迁入 `PersonEvent`，`Person` 上移除对应字段。
- 拒绝理由：需要数据迁移、前后端双改和兼容策略，超出本轮收益。

### D3: 关系摘要按读取时派生，输出“摘要卡 + 分组列表”双层结构

**选择**:
- 服务层在查询人物详情时继续拉取所有相关关系
- 在服务层或页面组装阶段额外计算关系摘要，例如父母数、配偶数、子女人数，以及是否存在双亲、婚配、后代等关键状态
- 页面展示保留现有父母/配偶/子女列表，但在其上增加一层摘要区，优先传达家谱位置

**原因**:
- 当前关系数据量小，读取时派生成本可控
- 摘要属于视图模型，不应反向写回数据库
- 可在不破坏当前关系操作组件的前提下升级人物页信息层次

**备选方案**: 新增持久化统计字段，例如 `spouseCount`、`childCount`。
- 拒绝理由：会引入冗余同步问题，后续修改关系时还要维护计数一致性。

### D4: 编辑体验采用“人物基础档案”和“事件维护”分区，而不是一次性超长单表单

**选择**:
- 保持现有人物编辑页作为单一入口，但将表单拆成基础信息、扩展档案、备注、事件列表几个分区
- 事件维护支持在编辑页内新增、删除、调整排序，优先采用内嵌列表编辑

**原因**:
- 用户心智仍然是“编辑这个人物”，不需要跳去单独事件管理页
- 分区后可以在现有 `PersonForm` 基础上演进，避免一个没有层次的超长表单
- 后续若要抽出 `PersonEventsEditor` 子组件，也更自然

**备选方案**: 为事件单独创建 `/person/[id]/events` 管理页。
- 拒绝理由：信息割裂，且本轮范围并未要求独立事件管理工作流。

### D5: API 写入采用显式嵌套 payload，避免前端分别命中多条端点

**选择**:
- `POST /api/persons` 与 `PUT /api/persons/[id]` 接受扩展后的 payload，其中包含人物档案字段和 `events` 数组
- 服务层在一次事务里完成 `Person` 更新与 `PersonEvent` 的替换式写入

**原因**:
- 人物编辑是单次保存动作，前端不需要协调多条请求
- 事务式写入可以避免人物更新成功、事件失败导致的局部落库
- 当前事件规模有限，替换式更新比细粒度 diff 更简单稳妥

**备选方案**: 为事件单独暴露 CRUD API。
- 拒绝理由：接口更多、前端状态管理更复杂，本轮并没有明显收益。

## Risks / Trade-offs

- **[扩展字段增多后表单复杂度上升]** → 通过分区布局、合理默认值和事件局部编辑降低认知负担
- **[字符串日期导致时间线排序不完全可靠]** → 约束 `dateLabel` 优先使用可比较格式（如 `YYYY` / `YYYY-MM` / `YYYY-MM-DD`），排序时提供“未知日期靠后”的兜底规则
- **[替换式事件写入可能覆盖并发编辑]** → 当前产品仍以单用户维护为主，可接受；如后续进入多人协作，再补并发保护
- **[别名使用数组字段后需要前端序列化处理]** → 在表单层统一使用字符串数组与 chip/tag 输入，不在服务层做隐式拆分

## Migration Plan

- 通过 Prisma schema 变更新增 `Person` 扩展字段与 `PersonEvent` 表
- 执行数据库迁移后，旧人物记录默认以空别名、空事件、空备注运行，不需要回填
- 发布顺序为：schema 与 API 先落地，再上线详情页与编辑页 UI
- 如需回滚，可移除对新增字段和事件表的读写代码；因为旧数据未被改写为新结构，不涉及复杂回迁

## Open Questions

- 本轮是否需要限制事件类型为固定枚举，还是允许“其他”类型配合自由标题录入
- 人物备注 `notes` 是否与现有 `bio` 在文案上做明确区分，例如“人物简介”与“维护备注”
