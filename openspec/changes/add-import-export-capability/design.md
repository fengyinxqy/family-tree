## Context

当前项目已经支持用户创建人物、维护原始关系、补充人物事件，并基于这些数据展示家族树和人物详情页，但还没有任何可供用户主动备份、迁移或恢复数据的机制。路线图已经把“导入导出能力”列为 V1.1 的主链路功能，因此这次设计要解决的不只是“生成一个 JSON”，还包括如何稳定地恢复这些数据、如何避免导入脏数据，以及如何给后续更多格式扩展留下边界。

现有约束包括：

- 数据由 `User`、`Person`、`Relationship`、`PersonEvent` 组成，且人物、关系、事件都依赖用户维度隔离；
- `Relationship` 当前只支持原始 `spouse` / `child` 两类持久化关系；
- 人物详情中的同辈关系是推导视图而非持久化记录，因此导入导出时只需要处理原始数据；
- 项目当前更需要“可恢复的系统内备份”而不是复杂的跨系统标准交换，因此首发方案应优先保证一致性和可用性。

## Goals / Non-Goals

**Goals:**
- 支持用户导出自己当前家谱空间中的完整核心数据到单个 JSON 备份文件。
- 支持用户从系统导出的 JSON 备份导入并恢复人物、关系和事件数据。
- 保证导入过程具备结构校验、权限隔离和事务一致性，避免半成功写入。
- 为未来 Excel / GEDCOM 等更多格式扩展预留统一服务边界与 payload 结构。

**Non-Goals:**
- 本轮不直接支持 Excel、GEDCOM、CSV 等外部标准格式。
- 本轮不处理跨账号共享导入、多人协作合并、增量同步。
- 本轮不尝试和现有数据做智能去重合并，默认导入到目标空间前先明确恢复策略。
- 本轮不导出推导型关系视图，例如兄弟姐妹摘要，只导出底层原始记录。

## Decisions

### D1: 采用“系统自有 JSON 备份格式”作为首发导入导出协议

**选择**:
- 定义一个版本化 JSON 文档，包含元信息和四类数据：人物、关系、人物事件、导出上下文；
- 导出接口返回该 JSON 内容，导入接口只接受该系统定义的 JSON 格式。

**原因**:
- 可以精确覆盖当前数据模型，不必为兼容外部标准先损失字段语义；
- 版本化格式便于未来平滑升级；
- 更容易做结构校验和测试。

**备选方案**: 首发直接支持 GEDCOM 或 Excel。
- 拒绝理由：格式适配复杂，且会把这轮目标从“可恢复备份”扩散到“通用互操作”。

### D2: 导入流程采用“先校验、后全量事务写入”的恢复模型

**选择**:
- 导入前先做 schema 校验、引用完整性校验和用户边界校验；
- 通过一次事务完成目标范围内的清空与重建，保证要么全部成功、要么全部回滚；
- 关系与事件通过备份中的稳定临时映射关系恢复到新创建的人物主键。

**原因**:
- 对于备份恢复场景，全量恢复比增量合并更易理解，也更可靠；
- 当前产品阶段单用户维护为主，事务式重建成本可接受；
- 避免导入一半失败后留下不可预测状态。

**备选方案**: 逐条 upsert 或增量合并。
- 拒绝理由：需要复杂的冲突检测与匹配策略，容易引入脏数据和隐性覆盖。

### D3: 导出内容只包含核心持久化域模型，不包含派生视图

**选择**:
- 导出 `Person`、`Relationship`、`PersonEvent` 及必要元数据；
- 不导出人物详情页里的推导型 sibling 视图、关系问答缓存或 UI 状态。

**原因**:
- 派生视图可以在恢复后重新计算，不应被当作源数据持久化；
- 减少备份体积与格式耦合；
- 有利于后续 schema 变更时保持导出协议稳定。

**备选方案**: 把人物详情聚合字段一起导出。
- 拒绝理由：这会把展示层语义混入备份协议，降低长期可维护性。

### D4: 能力边界收敛到专用 import/export 服务层与 API

**选择**:
- 新增独立服务模块负责导出 payload 组装、导入校验和恢复执行；
- API 路由只做认证、请求解析与响应封装；
- 前端入口后续可以挂在设置页、工具页或家谱工作台，不影响服务协议。

**原因**:
- 让导入导出逻辑不与人物/关系日常 CRUD 混杂；
- 更利于未来增加多格式适配器；
- 测试层可以直接验证服务逻辑，不依赖 UI。

**备选方案**: 把导入导出拼接进 `person.service` 等现有服务。
- 拒绝理由：职责会迅速膨胀，不利于后续扩展。

## Risks / Trade-offs

- **[全量恢复会覆盖目标空间现有数据]** → 通过明确的恢复语义、导入确认和事务回滚降低误操作成本。
- **[旧版本备份与未来 schema 演化可能不兼容]** → 在 JSON 中加入版本字段，并在导入时做显式版本检查。
- **[大体量家谱导入导出可能带来性能压力]** → 首发先按单用户常见规模设计，后续再按需要加入流式或分页策略。
- **[用户可能拿手工编辑过的 JSON 导入]** → 通过严格 schema 校验、引用检查和错误反馈阻断无效导入。

## Migration Plan

- 无数据库 schema 迁移要求。
- 先新增 JSON 协议、服务层和 API，再在合适 UI 位置接入入口。
- 首发部署后旧数据无需变更，导出可直接覆盖现有用户空间数据。
- 如需回滚，只需下线 API 与入口，不涉及数据结构回退。

## Open Questions

- 首发入口更适合放在家族树工作台，还是单独的设置/工具页面。
- 是否需要在导入前先提供“预检结果”预览，再执行实际恢复；本轮可以先做一次性导入并返回摘要。
