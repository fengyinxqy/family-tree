## Context

当前系统只持久化两类原始关系：`spouse` 与 `child`。家族树布局、人物详情页、关系问答引擎都建立在这套原始关系图之上，其中关系问答已经可以通过“共享父母”路径推导出兄弟姐妹，但人物详情页的关系展示仍然只覆盖父母、配偶、子女三类分组，关系维护 API 也没有显式封装“新增子女后补全同辈语义”的行为。

这次增强同时影响关系写入链路、人物详情数据组装和展示层，但不希望破坏现有树图布局，也不希望为了同辈关系再引入一类新的持久化边。仓库当前的约束包括：

- `Relationship` 表仅支持 `spouse` / `child` 两种原始关系；
- `src/lib/tree-layout.ts` 直接消费原始关系数据生成树边，如果写入额外同辈边会污染图布局；
- 关系问答引擎已经具备基于原始路径推导同辈关系的基础能力，新增能力应尽量复用这一事实而不是另起一套数据来源；
- 用户当前期望的是“维护关系后马上能看到结果”，而不是必须额外手工补一条“兄弟/姐妹”关系。

## Goals / Non-Goals

**Goals:**
- 在新增父母-子女关系后，系统能够自动识别受影响人物之间的同辈关系。
- 在人物详情页中展示同辈关系，使用“兄弟 / 兄妹 / 姐妹”这类对称标签表达。
- 保持家族树边线、`Relationship` 数据模型和现有关系问答主路径不被破坏。
- 将关系维护逻辑收敛到服务层，避免 API 路由继续直接散落 Prisma 写入与重校验逻辑。

**Non-Goals:**
- 不新增 `sibling` 持久化关系类型，也不修改 Prisma schema。
- 不在本轮区分“哥/弟/姐/妹”等长幼称谓；当前仅按组合性别输出对称同辈标签。
- 不修改家族树的连线规则，不为同辈关系绘制边。
- 不重构关系问答引擎的整体命名体系，除非实现过程中发现与详情展示存在必须统一的纯函数可复用点。

## Decisions

### D1: 同辈关系采用“读时推导”而不是“写时持久化”

**选择**:
- 新增 `child` 关系时只写入原始父母-子女边；
- 在详情查询时，根据当前人物的父母集合反查这些父母名下的其他子女，推导出同辈成员列表；
- 关系维护成功后通过页面重验证让详情页立即显示新的同辈关系。

**原因**:
- 与现有树布局兼容，不会产生额外边线；
- 避免同一事实被 `child` 与 `sibling` 双写，减少脏数据和同步复杂度；
- 与关系问答引擎当前“通过路径推理关系”的方向一致。

**备选方案**: 在 `Relationship` 表中新增 `sibling` 类型并同步创建记录。
- 拒绝理由：会直接影响树图构建、去重逻辑、API 契约和后续删除/修改关系时的联动维护成本。

### D2: 同辈标签使用对称聚合表达“兄弟 / 兄妹 / 姐妹”

**选择**:
- 两位同辈均为男性时标记为 `兄弟`；
- 一男一女时标记为 `兄妹`；
- 两位同辈均为女性时标记为 `姐妹`；
- 不根据 `birthDate`、`generationLabel` 或创建顺序进一步细分长幼。

**原因**:
- 当前模型没有可靠的长幼顺序字段，现有 `generationLabel` 也可能是代际而不是排行；
- 这套标签与用户需求里的“兄弟、兄妹、姐妹”保持一致；
- 对称标签更适合在详情列表中展示，不会出现“从 A 看是姐妹、从 B 看是兄弟”这类认知跳变。

**备选方案**: 直接复用关系问答引擎按目标性别返回的 `兄弟 / 姐妹` 标签。
- 拒绝理由：那套输出是问答语境下的定向称谓，不适合作为详情页里的成对关系标签，也无法覆盖“兄妹”。

### D3: 关系维护写入下沉到 `relationship.service`

**选择**:
- 扩展 `src/services/relationship.service.ts`，由服务层负责权限校验、重复校验、关系创建和路径重验证；
- `src/app/api/relationships/route.ts` 改为薄路由，只解析请求并调用服务层。

**原因**:
- 便于在一个地方集中处理后续关系维护增强；
- 降低 API 层与服务层逻辑漂移的风险；
- 更利于补充测试。

**备选方案**: 继续在 route handler 内直接写 Prisma。
- 拒绝理由：当前 API 已经开始承载越来越多关系维护规则，继续堆叠会让后续增强更难维护。

### D4: 人物详情查询返回显式的同辈视图数据

**选择**:
- 在 `getPerson` 的结果模型中增加 `siblings` 视图字段；
- 该字段由服务层在查询人物及其双向关系后组装，前端只负责展示；
- 列表项至少包含目标人物 `id`、`name`、`gender`、推导标签和用于解释的共享父母信息。

**原因**:
- 让详情页保持声明式，避免把关系图计算逻辑散落到页面组件；
- 后续如果关系问答、Agent、导出等也需要同辈摘要，可直接复用服务层或抽出的纯函数；
- 有利于编写单元测试。

**备选方案**: 页面层基于 `relationsA/relationsB` 自己现算。
- 拒绝理由：会让页面逻辑继续膨胀，也不利于 API/服务层的一致性。

## Risks / Trade-offs

- **[共享单亲也会被识别为同辈]** → 这是有意为之，规则定义为“同父或同母的既有子女”均视为兄弟姐妹。
- **[未区分长幼可能不够细]** → 当前先满足“有同辈关系可见”，待后续引入更稳定的排行语义后再细分。
- **[详情查询的派生计算增加复杂度]** → 通过抽出纯函数并增加测试来控制风险，当前数据规模下性能成本可接受。
- **[删除父母-子女关系后同辈摘要会变化]** → 这是推导模型的正常结果，依赖重新查询而非额外同步删除，反而更一致。

## Migration Plan

- 无数据库迁移。
- 先落服务层同辈推导与关系创建收敛，再更新人物详情页展示。
- 发布后通过现有 `revalidatePath` 机制让详情页和树页读取到最新关系视图。
- 如需回滚，只需移除服务层推导字段和详情展示，不涉及持久化数据清理。

## Open Questions

- 是否要在人物详情页额外展示“共享父亲/共享母亲/共享父母”的说明文案；本轮可先仅展示关系标签和人物名。
- 是否要把同辈关系也纳入 Agent 或关系问答的详情接口输出；本轮先以人物详情页为主。
